Observability · 2026

Building a self-hosted replacement for a managed log service on Grafana Loki

Problem

Log ingestion was the single largest line on the cloud bill, and production alerting depended on the same service, so it could not simply be switched off.

What I did

  • Designed and built Loki in Simple Scalable mode on ECS Fargate: object storage backend, replication factor 2 across two zones, long-term retention on tiered object storage.
  • Dual-shipped every service through Fluent Bit sidecars so existing alarms kept firing while parity was proven.
  • Split the read path into frontend, scheduler, querier pool and index gateway, with a custom Lambda autoscaler driven by in-flight sub-queries.
  • Found the new pipeline silently dropping batches during the parallel run. The system of record was unaffected. Traced it to a saturated write tier, resized, and held zero drops.

Measured

  • 8.43M vs 8.44M lines in a 30-minute reconciliation across 25 services (−0.06%)
  • 0 logs dropped and 52/52 alarms healthy on the 24-hour parity check
  • −80% bytes on the wire after enabling gzip (5.1×)
  • ~982,000 dropped batches a day in the new pipeline → 0 after the write-tier fix

API gateway · 2026

Moving the bank's API gateway from Kubernetes to ECS, in four environments

Problem

The Kong gateway ran on Kubernetes behind a service mesh, with custom plugins that needed renaming. Kong refuses to boot if the database names a plugin the image does not load, so the image swap and the data change block each other.

What I did

  • Built the image supply chain: upstream Kong 3.5 mirrored internally, 23 custom Lua plugins baked in, immutable tags, deploys triggered by a tag move and pinned to a commit.
  • Solved the boot-ordering constraint with an in-place rename, a backup table and reverse SQL per environment, proven on dev, then test, then UAT.
  • Built production on ECS with a Multi-AZ PostgreSQL database and single sign-on for the admin UI, ran it in parallel, then cut public traffic over by DNS.
  • Added identity-provider authentication in front of the gateway's management plane, with separate trust for production.

Measured

  • 4 environments cut over one at a time, production last
  • 44/44 identical status codes in the UAT parity smoke test; 2–4 ms on ECS against 8–16 ms before
  • Production: 471 routes and 258 services, counts equal to the source dump
  • Later hostname change on production done as a rolling deploy with both tasks healthy throughout

The plugins themselves were written by teammates. My part was the architecture, infrastructure, pipelines, migration and hardening.

FinOps · 2026

Taking the cloud bill apart, and building an agent that keeps doing it

Problem

Spend was hard to attribute. Nearly half of it carried no environment tag, and the obvious savings lists did not match what the bill would actually do.

What I did

  • Decomposed the bill by service, cluster, environment and application from billing and usage data, and traced anomalies to their callers.
  • Produced a prioritised savings catalogue: log pipeline, right-sizing, off-hours scheduling, storage lifecycle, data transfer.
  • Ran a read-only audit with twelve specialist agents and three review stages. Of 225 recommendations, 22 were rejected and 30 were duplicates before anything reached a human.
  • Found the nightly shutdown job had been failing silently for about ten weeks, and fixed it. Tooling now sits switched off for 43% of the week.
  • Built a standing read-only cost agent with a knowledge base, a savings ledger and a second agent that attacks its numbers.

Found

  • Savings worth 15–22% of the monthly run-rate identified
  • 71% of spend is shared platform cost; 45% has no environment tag
  • The provider's own recommendations cover about 4.6% of optimisable spend
  • Container right-sizing was worth $0 after discounts, because the commitment was already saturated

These are identified opportunities and implemented controls. I only publish a delivered saving once it has been re-measured on a later bill.

Database delivery · 2026

Making database changes ordered, checked and reversible

Problem

Schema scripts for twelve databases, used by 26 microservices, were promoted by moving files between branches. There was no ledger of what had run where, so environments drifted.

What I did

  • Designed one ordered changelog per database with Liquibase as the system of record, and a single promotion path: lint, validate, order check, snapshot, tag, run, verify.
  • Wrote pull-request lint rules, a head-of-queue guard for production, and a gate that stops an application deploying ahead of its schema.
  • Added a nightly drift report and a hash-verified plan, so what is approved is exactly what runs.
  • Worked through the rollback cases and wrote down the one that surprises people: a rollback does not un-ship a change, it puts the change back in the queue.

Measured

  • 56 of 56 automated checks pass in the proof of concept
  • 14 lint rules applied to every change before review
  • Drift designed to be detected within 24 hours
  • Runs on synthetic data in three local databases standing in for the environments

Status: architecture drafted for review and proof of concept complete. Not yet in production.

Field notes

Root causes, designs and smaller builds.

Shorter entries. Filter by the kind of work.

Root cause

A service advertised before it was listening

Service discovery published new task addresses 193 seconds before the process accepted connections, because the task had no container health check. A second fault was a restart loop with a 4 to 24 second margin between two health checks. Proved the mechanism in the same account and wrote an ordered fix.

Root cause

A database password that rotated itself

A managed secret rotated every seven days. Containers read secrets only at launch, so running tasks kept the old password and a non-production gateway lost its database for about an hour. Documented the event-driven design that makes rotation safe.

Root cause

Gateway timeouts that were not the load balancer's fault

A wave of 504s was blamed on scale-down. Four real deregistration events produced zero errors, which ruled that out. The cause was a database stall during a maintenance patch cascading through connection pools. A separate measurement showed a planned database upgrade was unnecessary.

Root cause

A function that timed out without telling anyone

A 128 MB function timed out on large files and raised no alarm. The same code ran in 2.19 seconds locally and over 60 on the platform. Memory was the CPU throttle. Resized it, and the backlog cleared.

Root cause

Why a slow batch job would not speed up with more CPU

The job was strictly serial with two synchronous calls per record, about three seconds each, so it was bound by latency and not compute. The useful fix was a claim step so each record is processed exactly once, not a bigger task.

Root cause

"Rename failed: access denied" on file uploads

The managed file-transfer service implements rename as copy then delete, and the role only allowed delete on a fixed list of prefixes. Only files over 100 KB were affected, because that is where the client starts using temporary names. Traced through audit events to a one-line policy fix.

Root cause

CI jobs queueing for a day, then being cancelled

Self-hosted runners updated themselves when a job was assigned and the one-shot container exited. Pinned the version, rebuilt the image and set a monthly rebuild so the platform keeps dispatching work.

Root cause

Deleting an API route did not disable the endpoint

A broader prefix route still matched and forwarded the full path. I read the router source to compute the actual priority, showed that "longest prefix wins" is false, and built two read-only checks that tell a matched route from a missing one by status code alone.

Root cause

A capacity debate about the wrong variable

A cache discussion was framed as an engine upgrade. Measuring key expiry and weekly memory peaks showed the real constraint was growth from keys that never expire, which no eviction policy can relieve, and that compute was never the limit.

The Price of a Safety Guarantee: The Audit Cost of Miss-Rate Certificates in LLM Triage of Security Alerts

When a model triages security alerts, most are closed and never looked at again, so nobody can see how many real vulnerabilities were closed by mistake. The accepted remedy is to audit a random sample of closures and publish a certified miss rate. This project asks a question that had not been computed for this setting: how much evidence does that certificate need?

The answer is a fixed number of audited misses. For a fixed relative precision and confidence, it does not depend on the miss budget, the audit rate or the length of the alert stream. On a public benchmark the whole corpus cannot supply it. A cheaper question, "is the miss rate over budget?", needs about 2.5 times less, although the benchmark is still short of that at a 3% audit rate. The practical reading: a one-off check of a triage system is within reach, keeping it continuously certified is not.

Stated limits. The formulas are classical. The contribution is the audit-cost analysis for alert triage and a reproducible instrument. Experiments use a logistic-regression scorer; the language-model tier is a small pilot. The guarantee covers raised alerts only: the scanner never flags 11.8% of the real vulnerabilities in the benchmark.

  • 24audited misses needed for one exact certificate
  • 55–77needed if the certificate must hold at every moment
  • 2.4available from the whole benchmark at a 3% audit rate
  • 10×shortfall between what is needed and what exists
  • 9.8audited misses to detect a miss rate at twice the budget
  • 89.2%miss rate a naive self-training triager drifts to

Research pilot · paused until after submission

Infrastructure time bombs: faults that are already there and have not failed yet

A time bomb is a fault that is already present in a working system and will become a failure at a later time without any new mistake by anyone. Each has three parts: a clock, a hidden coupling, and a trigger moment. The taxonomy comes from incidents I have worked on.

  1. T1Stale copy after rotationA credential rotates; something still holds the old one.
  2. T2Hard expiry not renewedA certificate, token or version reaches its end date.
  3. T3Cleanup of a referenced objectA lifecycle rule deletes something still in use.
  4. T4Growth to a hard limitMemory, disk or a quota fills at a steady rate.
  5. T5Third-party end of lifeA dependency's support window closes.
  6. T6Thin timing marginTwo timeouts a few seconds apart, until they are not.
  7. T7Retention-window lossState expires while its consumer is away.
  8. T8Silent stopSomething stops working and reports nothing.

Pilot on public data

  • 25 searches over public issue trackers to size each type
  • 400 issues sampled and double-labelled for two types (agreement κ = 0.89 and 0.91)
  • 31 of 200 rotation issues and 11 of 200 cleanup issues were real time bombs
  • Only 4 of 31 rotation cases could be detected from configuration alone
  • Scheduled rotation caused 4 of 31; manual rotation and tool side effects caused about half

Stated limits. Both raters were the same language model working from a written codebook, which inflates agreement, and they saw the first 700 characters of each issue. Counts are small and keyword-sampled. A human check is still required before any claim is made from this.

How the topic was chosen

I started with a crop-prediction and farmer-advisory system and dropped it after an honest review: the data could not be obtained and the scope was too large. I then scored the alternatives and, later, examined eighteen more ideas against the literature. None gave a stronger defensible topic than the alert-triage work. The gaps the search left open: operational time bombs, choosing which countries' data to learn from when predicting crop yield somewhere new, and how far ahead different classes of failure can be predicted at all.

Method

How I work.

Tested, cited or asserted

Every claim in a report carries one of three labels. If I ran it, it is tested. If a document says so, it is cited. Anything else is an assertion and is marked as one.

Attack the conclusion first

Before a recommendation leaves my desk, a second reviewer tries to break it. Several of my own headline numbers have been overturned that way, which is the point.

Rule things out in writing

A root cause is only credible next to the list of causes that were eliminated and how. A negative control beats a plausible story.

Correct in public

When a later measurement contradicts an earlier one, the report is revised with the correction shown. A withdrawn claim stays withdrawn.
